# `device_list` and client-rate reverse-engineering notes

Source: public MW6 HW2.1 firmware dump plus full MIPS disassembly generated by this repository's Actions workflow.

## Client inventory path

`device_list` imports `cmd_init`, `cmd_pub`, `cmd_sub`, Redis/CM infrastructure, DHCP/Wi-Fi/netlink helpers and maintains the client inventory.

Recovered publication API:

```c
cmd_pub(key, buffer, length)
```

Both `do_upload_client_list()` and `do_upload_one_client()` publish through:

```text
confctl_srv_key
```

The bulk path copies 124 bytes per `device_list` client record. The single-client path also copies one 124-byte record. Fields around +92/+96/+100 are state/time fields and must not be labelled as rates.

## Rate implementation located: `confsrv`

The second full-firmware scan located the previously missing implementation in:

```text
RootFS-unpacked/bin/confsrv
```

The binary contains the exact functions/strings:

```text
fill_cloud_info_device_lists_rate
fill_host_lists_rate
find_client_in_online_ip_info
print_online_ip_info
netlink_get_statistic_info
g_ip_info
```

This closes the earlier gap between `device_list` and the cloud/device representation.

## Kernel/user-space statistic transport

`libcommon.so` exports:

```c
netlink_get_statistic_info(...)
netlink_clear_statistic_info(...)
```

and owns global `g_ip_info`.

Disassembly of `netlink_get_statistic_info()` proves that the returned online-IP array uses **232 bytes per entry**. The function obtains the count, allocates `count * 232`, copies the records from the netlink reply into `g_ip_info`, and returns two 64-bit aggregate values plus the record count to its caller.

The kernel side exposes `online_ip_hash` / `online_ip_hash_size`. The firmware's `log_upload` utility independently confirms the readable procfs endpoint:

```text
/proc/net/online_ip
```

So `/proc/net/online_ip` is no longer a guessed path; it is explicitly used by the shipped firmware.

## Per-client rate calculation recovered

The function beginning around MIPS VA `0x437164` in `confsrv` corresponds to the rate-fill path (its diagnostic references line 2600 and the `NULL == g_ip_info` string used by `fill_cloud_info_device_lists_rate`).

Its behavior is now clear:

1. call `netlink_get_statistic_info()`;
2. retain a previous `g_ip_info` snapshot;
3. compute elapsed time between snapshots;
4. for each host/client, match its address to a 232-byte online-IP record (`find_client_in_online_ip_info` path);
5. compare two pairs of 64-bit counters from the current and previous record;
6. calculate a rate from `(current_counter - previous_counter) / elapsed_time`, followed by a firmware scaling constant;
7. write the resulting two client rates into the host structure.

The two source counter pairs in the matched 232-byte online-IP record are:

```text
+0x18/+0x1c  -> uint64 counter A
+0x20/+0x24  -> previous/snapshot counter A
+0x28/+0x2c  -> uint64 counter B
+0x30/+0x34  -> previous/snapshot counter B
```

The calculated 32-bit rates are written to the cloud/host record at:

```text
host + 0x98 (152)
host + 0x9c (156)
```

This is the first direct code-level proof of the two per-client traffic-rate values. Direction (upload vs download) still needs one controlled live correlation before assigning names; we will not guess it.

## Current architecture

```text
DHCP / Wi-Fi / mesh
        |
   device_list
        | identity / MAC / node / state
        v
     confsrv
        ^
        |
libcommon netlink_get_statistic_info()
        ^
        |
BM / online_ip kernel statistics
        |
/proc/net/online_ip
        |
232-byte g_ip_info records
        |
64-bit counter deltas / elapsed time
        v
host +0x98 / +0x9c = two per-client rates
```

## What remains before HA sensors

The missing pieces are now much smaller:

1. identify which of host `+0x98` and `+0x9c` is download and which is upload;
2. recover the exact scaling constant/unit (likely a byte/bit or KiB-style conversion, but this must be proven from `.rodata` or a controlled sample);
3. determine the safest remotely reachable read-only path. `/proc/net/online_ip` is ideal if a supported shell/agent path is available; otherwise decode `confsrv`/`cmdsrv` read-only retrieval rather than using cloud upload commands;
4. implement the HA coordinator only after these values are verified.

## Safety

No unknown cloud upload command, SET operation, or destructive router action is used. Reverse engineering remains passive/offline until a positively identified read-only operation is available.
