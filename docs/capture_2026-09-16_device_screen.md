## Cloud flow

The largest relevant application flow after local initialization is TCP to `8.209.102.224:11822`. In this capture the server-to-app direction carries about 51 KB of TCP payload. This supports the working hypothesis that the mobile application's client/device view is fed through the Tenda ucloud channel rather than by a simple post-login local TCP/9000 GET.

This is correlation from the capture, not yet proof of the cloud message schema.

## SYS BASIC INFO (`module 0x01 / command 0x00`)

The 353-byte response is protobuf-like. The outer message begins with:

- field 1 varint = 0 (status/result)
- field 2 length-delimited = 348 bytes

The nested object starts with an 18-character device identifier, followed by additional nested capability/state records. It does **not** resemble a per-client list: no repeated MAC/IP/hostname records were found in this response.

The identifier itself is intentionally not duplicated in this repository.

## Conclusion

The capture rules out the simplest model:

```text
LOGIN -> local GET clients on :9000
```

for this app interaction. Current evidence instead fits:

```text
device_list -> internal cmd/pub-sub -> ucloud/cloud-info -> Tenda cloud :11822 -> mobile app
```

The next reverse-engineering target is therefore the internal publication generated by `device_list` (`do_upload_client_list` / `do_upload_one_client`) and the ucloud `M_CLOUD_INFO` serializer, not blind probing of TCP/9000 command IDs.
